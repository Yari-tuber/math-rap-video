# 音频：由用户或客户自己提供

本流程不绑定任何音乐或配音平台。客户交来**一条带人声的音频**，脚本负责把时间算出来。用哪家模型、用谁的声音、要不要真人，都由客户决定。这份文件有三部分：发给客户的要求、可选的制作方式、收到音频后怎么验收。

## 一、发给客户的要求（可以直接转发）

> **需要您提供**
> 1. 一个音频文件（mp3 或 wav），内容是把我们确认过的歌词**按顺序、一字不改**唱或念出来
> 2. 如果方便，再给一份字幕文件（SRT）。没有也可以，我们自己识别
>
> **制作时请注意**
> - **速度固定**，建议 90 BPM 左右（80–100 都可以），全曲不要变速
> - **一句歌词唱一小节**（90 BPM 时约 2.7 秒一句）。歌词已经按这个长度写好了
> - **吐字要清楚**，尤其是口诀那两句。宁可少一点旋律，也要听得清每个字
> - 前奏不要超过 2 小节（约 5 秒），我们会把前奏剪掉，让人声一开头就进
> - 不要加歌词以外的念白、和声重复、"yeah / uh" 这类垫词
> - 结尾人声唱完后留 1 秒以上再结束
>
> **风格参考**（给 AI 音乐平台用）
> `Chinese melodic rap, sing-song chant, two-note melody, mid-high male voice, light autotune, tight on-beat flow, 90 BPM, minor key, trap hi-hats, soft piano, clear diction`
> 歌词里保留 `[Verse 1]` `[Hook]` `[Verse 2]` 这三个段落标签。

## 二、可以怎么做（客户自己选）

| 方式 | 做法 | 特点 |
|---|---|---|
| **AI 音乐平台一次生成** | 把歌词和风格词贴进去，人声和伴奏一起出 | 最省事。建议多生成几版挑最清楚的 |
| **真人说唱 / 朗读 + 伴奏** | 找一条 90 BPM 的伴奏，跟着节拍录人声，再混在一起 | 咬字和情绪最可控，适合老师本人出声 |
| **AI 配音 + 伴奏** | 用 TTS 或声音克隆按句念出来，剪到每句一小节，叠在伴奏上 | 声音固定、可批量；节奏感弱于真正的说唱 |
| **纯讲解配音** | 不要说唱，正常语速讲解，可以配轻音乐 | 画面流程完全一样，处理时加 `--no-beat` |

常见的 AI 音乐平台有 Suno、海绵音乐、Mureka、天工 SkyMusic、ElevenLabs Music 等。**我们只实测过 ElevenLabs Music**（结果见下），其他平台没有测过，不做优劣判断。选择时主要看三点：中文咬字是否清楚、是否允许商用、价格。版权和商用授权由提供音频的一方自己确认。

### 用 AI 音乐平台时的经验（来自 ElevenLabs 的 5 次实测）

- **旋律越强，吐字越糊。** "念唱"风格好听，但声调容易丢。所以口诀要单独成段，并要求唱慢、唱清楚
- **同样的输入，结果不稳定。** 5 版里有 2 版人声晚进了 2 小节，把后面的歌词挤在一起。所以一次至少生成 2–3 版
- **每句字数决定节奏。** 平台大多不能指定"每句几秒"，一句一小节主要靠歌词字数控制（11–15 字）
- 原理段每句写短一点（9–11 字），结尾才不会挤

### 可选：脚本直接调用 ElevenLabs

只在用户明确要求、并提供自己的 API Key 时使用。每版约消耗 1000 额度（约 70 秒的歌）。

```bash
export ELEVENLABS_API_KEY=...            # 用户自己的 Key
python $SKILL/scripts/gen_music.py <作品目录> --bpm 90 --preset chant --takes 2
```

它按段落给时长（每句一小节），所以比网页上生成的更容易做到一句一小节。`--preset chant` 是念唱，`--preset boombap` 是低沉说唱（吐字最清楚，旋律最少）。

## 三、收到音频后：算时间、验收、挑选

### 拿到字幕（SRT）

任选一种，结果都能用：

- 平台或客户直接给的字幕文件
- 剪映：导入音频 → 识别字幕（或"文稿匹配"贴入歌词）→ 导出 SRT
- 任何语音识别工具（Whisper 类、各家云服务、本地 ASR）导出的 SRT
- 带逐字时间的 JSON（`words: [{text, start_time, end_time}]`）用 `--words`，最精确

识别结果**有错别字没关系**：唱腔常被听成同音字（"减一"听成"简易"），脚本按字对齐，对不上的字在前后之间插值。字幕的断句和歌词不同也没关系。装了 `pypinyin` 的话会按拼音匹配，更耐同音字。

### 运行

```bash
python $SKILL/scripts/prepare_audio.py <作品目录> --audio 歌.mp3 --srt 识别.srt --bpm 90 --intro-bars 2
```

`--intro-bars` 是和客户约定的前奏小节数（我们要求不超过 2）。写了它，脚本才能判断"人声是不是进晚了"。

### 读输出

最后一行是**结论**。"建议换一版"时会写明原因，退出码是 3：

| 原因 | 说明 |
|---|---|
| 某句很可能漏唱 | 那一句几乎没有时长，或和歌词基本对不上。AI 生成的歌偶尔会吞掉一句 |
| 人声比约定的前奏晚进 | AI 平台的随机现象。晚进以后后面的歌词会被挤 |
| 整体被压缩 | 24 句只唱了 20 小节这种情况，句子会越来越赶，吐字多半也糊 |
| 多句匹配率低 | 音频没按歌词唱，或歌词文件拿错了 |

结论是"可用"时再看逐句的表：

| 列 | 含义 | 怎么看 |
|---|---|---|
| 起止时间 | 这句从几秒唱到几秒 | 每句时长应该差不多 |
| 拍位 | 这句开头落在小节里的第几拍（0–4） | 离小节头不到半拍（≤0.5 或 ≥3.5）算"落在小节头"，脚本按这个标准数出"落在小节头的句子 x/24"；3.0–3.5 是略微抢拍，常见，不影响使用；1–3 之间说明这句明显抢拍或拖拍了 |
| 匹配 | 识别出来的字和歌词对上的比例 | ≥90% 很可靠；50–90% 时间可能偏 0.3 秒以内；<50% 是推算的，要请人听 |

精度参考（数线段项目实测）：用普通识别字幕时，24 句里 22 句的起点误差在 0.15 秒内，识别错得多的 2 句约 0.3 秒；用逐字时间时基本没有误差。

### 有几版时怎么挑

每版写到不同的文件：

```bash
python $SKILL/scripts/prepare_audio.py <目录> --audio 生成_01.mp3 --srt 01.srt --bpm 90 --intro-bars 2 --out timing_01.json
python $SKILL/scripts/prepare_audio.py <目录> --audio 生成_02.mp3 --srt 02.srt --bpm 90 --intro-bars 2 --out timing_02.json
```

按这个顺序比，前一条分不出高下再看后一条：

1. **结论是"可用"**。"建议换一版"的直接排除
2. **口诀清楚**：看口诀那两句（第一次出现和 Hook 段）的匹配率，以及识别出来的字是不是口诀本身。口诀唱错或唱糊的版本，节奏再整齐也不要。这一条排在节奏前面：一版口诀清楚但落在小节头的句子少几句，另一版节奏整齐但口诀匹配率低，选前一版
3. **没有匹配率低于 50% 的句子**，或者这样的句子更少
4. **落在小节头的句子更多**
5. 还分不出来：加 `--deep` 看卡拍偏差，小的更整齐；或者请人听

选定后把那一版复制成 `timing.json`（`cp timing_02.json timing.json`）。

这些都是从识别结果推断的。**口诀到底清不清楚，最终要人听一遍**，交给用户时要说明这一点。

### `--deep`

会用 `demucs` 分离出人声，量每个字的起点离节拍网格有多远，输出"卡拍偏差中位数"。要多跑几分钟；分离出的临时文件测完会自动删除。参考值：我们仿的那条原版视频是 12.5 毫秒，随口乱念大约 42 毫秒。只在两版难分高下时用。

### 没有字幕时的退路

```bash
python $SKILL/scripts/prepare_audio.py <作品目录> --audio 歌.mp3 --grid --entry 5.3 --bpm 90
```

按"一句一小节"从人声进入点往后推。只适合节奏很规整的歌（实测 24 句里 22 句误差在 0.16 秒内，另外两句差到 0.4–0.7 秒）；`--entry` 要听一下或看波形确定。

### 换音频

客户换了一版音频：把新文件放进作品目录，重跑 `prepare_audio.py`，然后直接 `check` → `sheet` → `build_video`。分镜和图形不用改，因为它们的时间都是相对歌词写的。
